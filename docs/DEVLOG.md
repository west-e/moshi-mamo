# 開発記録

設計判断・失敗例・変更内容・変更前後の測定を簡潔に残す。数値は少数の架空シナリオでの結果であり、一般的な精度ではない。

## 2026-11-02 最小の一通りの流れ（模擬入力 → Claude 判定 → 画面・音）

### 構成の判断
- **Node + TypeScript 1リポジトリ**（Hono の判定サーバー + Vite/React の画面）。DB なし。会話本文はブラウザのメモリにだけ置き、サーバーログには件数・判定・時間のみを出す。
- **判定は毎回ステートレス**: その時点までの発話だけを渡す。前回の判定結果も渡さない（前の判定に引きずられないようにし、未来の情報の混入経路をなくすため）。
- **構造化出力**（`betaZodOutputFormat`）で `signals → injection_suspected → rationale → level` の順に出させる。根拠を先に書かせてから結論を出させる。
- **利用者画面にはモデルの生成文を出さない**。レベルと兆候の種類から、検証済みの定型文を選ぶ。短く保つためと、会話中の命令文が画面に届かないようにするため。
- **注意は通話中に下げない（ラッチ）**。表示がちらつくと高齢の利用者が混乱するため。判定ごとの生の値は開発画面に出す。
- **状態を分ける**: 待機 / 確認中 / 兆候なし（安全の保証ではない、と明記） / 注意 / 強い注意 / 判定不能 / 確認できなかった / 接続が切れている。エラー時は「見守りが止まっています」と出し、安全だと誤解させない。
- **プロンプトインジェクション対策**: 文字起こしは `<transcript>` 内のデータと明示し、本文中の `<>` は全角にして区切りを壊せないようにした。操作を試みる発話は `injection_suspected` として記録させる。
- **モデル**: 既定は `claude-opus-5-5`（effort `low`）。`MOSHI_MODEL` で切り替えられる。Sonnet 5.5 / Haiku 5.5 との比較は、調整用シナリオで遅延と精度を測ってから決める。拒否時のサーバー側フォールバック（`fallbacks: "default"`）を有効にしている。

### Claude 判定の初回評価 — 調整用5本（claude-opus-5-5 / effort low）
プロンプトは初版のまま。調整前の基準値として残す。

| シナリオ | Claude の推移 | 単語一致の推移 | Claude の結果 |
|---|---|---|---|
| T1 家族の週末 | `・・・・・・・・・` | `・・・・・・・・・` | OK |
| T2 家族と旅行代金 | `・・・・・・・・・・` | `・・注注注警警警警警` | OK（単語一致は誤警告） |
| T3 警察を名乗る | `・・注注注注警警警警警警警警警警` | `注注注注注注警警警警警警警警警警` | OK。注意は3（逮捕・名簿で不安をあおる）、強い注意は7（銀行名とカード枚数を聞く） |
| T4 曖昧（役所） | `・・注注注・?注・` | `・・注注注注注注注` | OK（許容範囲内）。ただし判定ごとに揺れる |
| T5 操作を含む | `・・注警警警警警` | `注注注注注警警警` | OK。見守りAIへの指示（発話4）で操作の試みを検知し、強い注意へ |

- 合格: Claude 5/5、単語一致 3/5
- 応答時間（サーバー計測, 52回）: p50 3.2s / p95 5.0s / 最大 7.6s、判定エラー 0
- ブラウザでも T5 を自動再生し、発話3で注意、発話4で強い注意に切り替わることを確認した。根拠の発言が強調され、「操作の試みを検知」が表示された。

気づいた点（次の改善候補）:
1. **調整用が易しすぎる**: 5/5 では改善の余地が見えない。話者が「不明」のもの、文字起こしの誤り、本物の金融機関からの正当な連絡など、難しい調整用シナリオを足す必要がある。
2. **遅延**: 1発話ごとに3〜5秒かかる。自動再生（3.5秒間隔）では、ほぼ常に「確認中」が出る。モデルと effort の比較が必要。
3. **T4 の揺れ**: 生の判定が「注意 → なし → 判定不能 → 注意 → なし」と揺れる。利用者画面は注意を下げない方式なので表示は安定するが、曖昧な電話で一度出た注意がそのまま残る。
4. 見守りへの操作は兆候の種類としては `other` になる。開発画面では「操作の試みを検知」として別に表示している。

### 調整用シナリオの追加（5本 → 9本）
初回評価で 5/5 となり、改善点が見えなかったため、難しい調整用シナリオを4本足した。
- T6 本物の銀行からの案内（「キャッシュカード」「暗証番号」が出るが正当）
- T7 息子を名乗る詐欺（話者がすべて「不明」、聞き間違いを含む）
- T8 娘から父のけがの連絡（急ぎだが正当）
- T9 暮らしのアンケートを名乗り、一人暮らしや自宅の現金を尋ねる（曖昧）

### 速さの検討: 判定専用モデル（Jev）ではなく Claude 内で「判定だけモード」
- 利用者から、判定だけを返すモデル（TypeSafe AI の Jev）のほうが速いのでは、という提案があった。紹介記事には速度・日本語対応・会話の扱い・データの送信先についての記載がなく、外部サービスが増える。そのため、ハッカソンの方針（Claude で完結）に沿って見送った。
- 代わりに考え方を取り入れ、Claude に説明文を書かせず「レベル・兆候の種類・根拠の発話番号」だけを返させる **判定だけモード（quick）** を追加した（`server/assess.ts` の `PRESETS`）。

| Opus 5.5・判定だけ | 8/9 | 1 | 0 | 2.0s | 3.2s | 72 | $0.0036 |

分かったこと:
- **判定だけモードでも正しさは落ちなかった**（Opus は理由つきと同じ推移）。説明文をやめるだけで、p50 は 3.1s から 2.0s に下がった。
- **Haiku 5.5・判定だけ** は p50 1.1s・p95 1.9s で、正しさは Opus と同じ 8/9。1判定の費用は約60分の1。
- Sonnet は、孫からの普通の電話の第一声（「おばあちゃん？ゆうただよ」）で注意を出した。オレオレ詐欺の出だしと区別できていない。
- 思考なしにすると、速さはほとんど変わらないまま、「判定不能（?）」の揺れや第一声での注意が増えた。思考なしの利点は小さい。
- 単語一致は、本物の銀行の案内（T6）でも「強い注意」を出し、息子を名乗る詐欺（T7）は「強い注意」に届かなかった。

**全モデル共通の失敗: T8（娘から父のけがの連絡）で注意が出たまま残る。**
- 第一声「お父さんが転んで病院にいる」の時点で、どのモデルも注意（または判定不能）を出す。発話1の時点だけを見れば、事故を装う詐欺の出だしと区別できないため、判定としては無理もない。
- その後の生の判定はすべて「なし」に戻る。しかし利用者画面は注意を下げない方式なので、正当な電話の最後まで「ちょっと待って」が残る。
- → モデルではなく **表示の方針（注意を下げない）の問題**。ラベルを緩めて合格扱いにはしない。表示の方針の見直しを次の課題にする。

注意: 9本の結果なので、8/9 と 8/9 の差は区別できない。モデルの選択は、速さ・費用・揺れの少なさを合わせて判断する。

**決定（利用者と合意）: リアルタイム判定の既定を `haiku-quick`（Haiku 5.5・判定だけ・思考あり）に変更。**
- 理由: 正しさは Opus と同じで、速さは約2倍、費用は約60分の1。ハッカソン後も使い続けられる費用（10分の通話で約100判定 ≒ $0.01）。思考なしは速さの利点が小さく、揺れが増えるため採らない。
- 他の設定は `MOSHI_PRESET` で切り替えられる。
- ブラウザで T7 を自動再生して確認した。判定は1回 0.9〜2.4s で、自動再生（3.5秒間隔）でも判定待ちがたまらない。発話2で注意、発話5で強い注意。
- 気づいた点: Haiku は兆候の種類のラベルが粗い。例えば発話5（かばんを置き忘れた）に「口止め」を付けている。根拠の表示は開発画面だけなので利用者画面への影響は小さいが、デモで見せる際は注意する。

### 表示ルールの見直し: 正当な電話で注意が最後まで残る問題
**変更前**: 一度出た注意（caution）も強い注意（warning）も、通話中は下げない。
→ T8（娘から父のけがの連絡）では、第一声で出た注意が、正当だと分かった後も最後まで残った。

**変更後**（`shared/display.ts`。画面と評価が同じルールを使う）:
- 強い注意は、これまでどおり通話中は下げない。
- 注意は、その後「なし」が3回続いたら解除する。解除後の画面は「いまは 気になる点は ありません／さきほどの話で 不安が残るなら 家族に 確かめて」とし、注意が出たこと自体はなかったことにしない。
- 判定不能・エラーは「なし」の連続に数えない（確かめられていないことを解除の根拠にしない）。
- 「判断が つきません」は判定不能が2回続いたときだけ出す。Haiku は単発の判定不能で揺れることがあり、そのたびに画面が変わるのを防ぐため。通信・判定の失敗はこれまでどおりすぐ出す。

**採点の変更**: 正常な電話は「強い注意が一度でも出る」または「最後に注意が残る」と不合格にした。一時的な注意（出た後に解除）は不合格にしないが、件数を別に数える。詐欺の電話で注意が途中解除されたら不合格（新しい失敗の型）。同じ判定結果から3つの表示ルールを計算して比べた（API の追加呼び出しなし）。

| 方式 | 表示ルール | 合格 | 誤警告・過剰 | 正常な電話での一時的な注意 | 見逃し・遅れ | 詐欺で途中解除 |
|---|---|---|---|---|---|---|
| Opus・判定だけ | 下げない（変更前） | 8/9 | 1 | 0 | 0 | 0 |
| Opus・判定だけ | なし2回で解除 | 9/9 | 0 | 1 | 0 | 0 |
| Opus・判定だけ | なし3回で解除（採用） | 9/9 | 0 | 1 | 0 | 0 |
| Haiku・判定だけ | 3ルールとも | 9/9 | 0 | 0 | 0 | 0 |

- 2回と3回の差は今回の9本では出なかった。詐欺で途中解除されにくい側を取り、3回を採用した。
- ブラウザで T8 を再生して確認した。発話1で「ちょっと待って」、発話2の単発の判定不能では表示を変えず、発話3〜5の「なし」3回で解除後の表示に変わった。

**新たに分かったこと: 同じ設定でも実行ごとに結果が揺れる。**
- Haiku の T8 は、前回の測定では発話7で注意、今回は発話1で判定不能。ブラウザでは発話1で注意になった。
- 今回の測定では、Haiku で判定エラーが1回出た（T5 の最後の発話）。
- → 1回の測定の合否で設定を決めるのは危うい。次の改善では、同じシナリオを複数回流して、揺れの幅を測る。エラーの種類も記録する。

### 公開リポジトリ向けの安全策
- `scripts/check-secrets.mjs` を git の pre-commit フック（`.githooks/`、`core.hooksPath`）から実行する。`.env`・音声ファイル・APIキーらしき文字列を含むコミットを止める。Claude Code が行うコミットにも、利用者が手で行うコミットにも効くよう、Claude Code 専用のフックではなく git のフックにした。
- 偽のキーを含むファイルで止まること、空の `ANTHROPIC_API_KEY=` は通ることを確認した。
